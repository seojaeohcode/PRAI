# PRAI는 어떻게 시작됐나 — croScan 홍보 영상 제작기

PRAI는 2026년 10월 30일에 만든 croScan 홍보 영상에서 시작했습니다.
croScan은 조선소 위험작업허가서를 AI가 미리 검토하는 웹앱입니다.
이 문서는 그때 실제로 한 방식을 순서대로 적고, PRAI가 그 방식을 어떻게 바꿨는지 정리합니다.

> 영상: 1920×1080, 30fps, 64.5초, H.264 + AAC, −14 LUFS. 인트로 28박 → 시연 6장면 → 엔딩 20박.

---

## 1. 출발점: 레퍼런스 4개

사용자가 유튜브 링크 4개를 줬습니다. Claude Code가 브라우저로 영상을 보고 화면을 찍어 배울 점을 정리했습니다.

| 레퍼런스 | 배운 점 | 영상에 쓴 곳 |
|---|---|---|
| [땡쓰 앱 서비스 홍보영상](https://www.youtube.com/watch?v=5d_dLmf7MMU) | 필요한 기능을 확대하고 박스로 짚는 시연 편집 | 시연 장면의 카메라 확대·강조 박스 |
| [‘seven’ ident](https://www.youtube.com/watch?v=eavioeC_ge0) | 유광 도형, 물리감 있는 움직임, 도형이 화면을 덮는 전환, 링이 로고가 됨 | 구체, 원형 전환, 로고를 감싸는 링 |
| [플래니 홍보영상](https://www.youtube.com/watch?v=e6WOAiOGFA4) | 박마다 바뀌는 단어, 크게 깔린 외곽선 글자, 칩, 동심원, 리본 엔딩 | 단어 컷, 외곽선 글자, 칩, 동심원, 리본 |
| [MAKE IT FUNKY NOW](https://www.youtube.com/watch?v=bcoPG0oSqPI) | 디자인이 아니라 리듬: 모든 변화가 비트에 딱 들어옴 | 박자 엔진 전체 |

원칙은 하나였습니다. **디자인은 베끼지 않고 방식만 가져온다.**
그래서 영상의 고유 모티프는 croScan이 실제로 하는 일에서 만들었습니다.
두 작업의 시간 막대가 겹치고, 스캔선이 지나가고, 로고로 모이는 흐름입니다.

## 2. 실제로 한 순서

1. **콘티**: 9장면표와 자막을 `STORYBOARD.md`에 썼습니다. Codex에게 콘티를 검토받았습니다.
   Codex는 없는 기능을 말하는지, 숫자가 과장인지, 자막이 3초 안에 읽히는지를 봤습니다.
2. **화면 캡처**: 실제 croScan 스테이징 서버를 헤드리스 Edge로 조작하며 9장을 찍었습니다(2배율).
   직접 만든 작은 CDP 드라이버(`cdp2.mjs`)와 캡처 스크립트(`capture.mjs`)를 썼습니다.
   찍을 때 화면 요소의 위치를 `rects.json`에 같이 저장해서, 확대할 곳을 숫자로 알 수 있게 했습니다.
3. **장면 코드**: Remotion(React)으로 장면을 하나씩 코드로 짰습니다.
   카메라 확대(`useCamera`), 강조 박스(`Mark`), 클릭 표시(`Click`), 자막(`Caption`)을 부품으로 만들었습니다.
4. **내레이션**: 오픈소스 edge-tts로 한국어 음성(SunHi, +6%) 9줄을 만들었습니다.
   "croScan"은 "크로스캔"으로, "50건"은 "쉰 건"으로 적어 읽히는 대로 발음되게 했습니다.
5. **배경음악**: 무료 음원 후보 7곡을 분석했습니다. 박이 가장 또렷하고 처음부터 에너지가 일정한 곡을 골랐습니다.
   Kevin MacLeod의 "Getting it Done"(CC BY 4.0)입니다. 유튜브 영상의 소리는 허락이 없어서 쓰지 않았습니다.
6. **박자 맞추기**: 사용자가 "비트에 맞춰 딱 들어오는 쫀득한 모션"을 원했습니다.
   그래서 모든 장면이 박에서 시작하고 박에서 끝나게 다시 짰습니다.
   카메라는 1박 동안 움직여 박에 도착하고, 강조 박스는 박에 튀어 들어오고, 장면 전환은 박에서 컷합니다.
   인트로와 엔딩은 Codex에게 박자표를 설계받아 모션그래픽으로 새로 만들었습니다.
7. **렌더와 마무리**: Remotion으로 렌더한 뒤 ffmpeg로 음량을 −14 LUFS(유튜브 기준)에 맞추고 색 범위를 bt709로 바꿨습니다.
8. **검수**: 영상을 0.25초 간격 프레임 묶음 3장으로 만들어 Codex에게 두 번 검수받았습니다.
   "인트로 첫 4초와 엔딩이 약하다"는 지적을 받아 고쳤습니다.

## 3. Codex와 협업한 방식

| 회차 | 맡긴 일 | 결과 |
|---|---|---|
| 콘티 검토 | 실제 앱 코드와 콘티를 비교해 없는 기능·과장 찾기, 자막 9줄 권장 | 자막을 Codex 권장안으로 교체 |
| 모션 박자표 | 인트로 28박·엔딩 20박의 박별 화면·움직임·문구 설계, 과장 표현 지적 | "충돌·충격파" → "검토 필요"로, "현장에 알립니다" → "현장 게시 서류까지"로 |
| 프레임 검수 1·2 | 프레임 묶음을 보고 리듬·가독성 문제 최대 8개 | 첫 장면을 박마다 덩어리로 찍히는 제목으로, 로고에서 멈추던 2.6초를 시연 화면으로 이어지게 |

Codex는 항상 읽기 전용으로만 썼습니다. 만드는 일은 모두 Claude Code가 했습니다.
이 방식이 PRAI의 역할 분배([roles.md](../roles.md))가 됐습니다.

## 4. 한계와 PRAI의 해법

이 방식은 영상 한 편을 만들기에는 충분했습니다. 하지만 다른 제품에 다시 쓰기는 어려웠습니다.

| croScan 때의 한계 | PRAI의 해법 |
|---|---|
| 장면 안의 시간이 프레임 숫자로 박혀 있어서, 곡을 바꾸면 모두 다시 계산해야 했음 | 스펙의 모든 시간을 **박**으로 씁니다. 곡을 바꾸면 박 길이만 바뀝니다 |
| 인트로·엔딩이 300줄짜리 손코딩 JSX라 다시 쓸 수 없었음 | 인트로·엔딩을 **블록 17종의 큐 목록**(박자표)으로 씁니다 |
| BPM·첫 박·내레이션 길이를 손으로 적었고, BPM 측정 스크립트는 사라졌음 | `prai beat`가 BPM·첫 박·마디 위치를 재고, `prai voice`가 길이를 재서 잠금 파일에 적습니다 |
| 캡처 드라이버가 임시 폴더의 자작 스크립트였고 croScan 내부 함수에 묶여 있었음 | `prai capture`가 Playwright와 설치된 Edge/Chrome으로 JSON 캡처 계획을 실행합니다 |
| 자막이 짧은 헤드라인 하나뿐이었음 | 헤드라인과 말 자막(TTS 문장 타이밍 사용)을 두 층으로 둡니다 |
| Codex 검토가 즉흥 프롬프트였고, 회차와 판단 기록이 없었음 | `prai review`가 프롬프트 템플릿·모델·추론 강도·회차 상한을 지키고, 판단은 ledger에 남습니다 |
| 1920×1080·색·폰트·주소창 문구가 하드코딩이었음 | 테마 토큰과 설계 좌표(1920×1080 → 출력 크기로 균일 축소) |

## 5. PRAI가 찾아낸 croScan 영상의 오차

PRAI의 박자 분석기를 croScan 때 쓴 곡에 돌려 보니 **135.00 BPM**이 나왔습니다.
그때는 136 BPM으로 맞췄습니다. Codex도 곡의 공식 페이지에서 135 BPM을 확인했습니다.
1 BPM 차이는 64초 동안 약 1박만큼 어긋납니다.
그래서 croScan 영상은 뒤로 갈수록 박이 조금씩 밀렸을 것입니다. 당시 "큰 변화 32곳 중 17곳만 박 ±2프레임 안"이라는 측정 결과도 이것과 맞습니다.
첫 박 위치(0.02초)는 그때 손으로 맞춘 값과 분석기가 찾은 값이 같았습니다.
같은 곡을 쓴 PRAI의 Excalidraw 예제는 135 BPM으로 맞췄고, 같은 측정에서 37곳 중 27곳(73%)이 박 ±2프레임 안에 있었습니다.
나머지는 대부분 카메라가 움직이는 도중(가장 빠른 지점)입니다. 카메라는 박에 "도착"하도록 만들었기 때문에, 움직임이 가장 큰 순간은 박 사이에 옵니다.

## 6. 원본 자료

croScan 저장소는 비공개라서 PRAI 저장소에는 croScan 화면을 넣지 않았습니다.
대신 같은 방식으로 만든 예제 세 편(Excalidraw, Shipnote, PRAI 자기소개)을 넣었습니다.
